SPECTRA on Spec Kit

Spec Kit gives you the loop. SPECTRA fills in what the loop assumes you already have.

SPECTRA is a Spec Kit extension. It replaces nothing: specify, plan, tasks, and implement still do the core work. SPECTRA agents sit around them, before the first spec, between the phases, and after the build. Each one reads your project, asks you what it cannot work out, writes a document for you to review, and hands off to the next command.

Before the first spec

Domain, methodology, test and deployment strategy, and imported team knowledge, all feeding a constitution that reflects how the project really works.

Between the phases

BRDs and impact analysis before specify, test plans after it, ADRs during planning. Each one is an input the next core phase reads.

After the build

UAT with saved evidence, pull requests opened and reviewed against the spec they carry, and root-cause analysis when something breaks.

01Scenarios

Pick the situation closest to yours.

01

Building the constitution

The situation: your first time on a brownfield project. There is a codebase, years of history, and a pile of documents that live outside the repository: an architecture deck, a QA handbook, a hosting standard from the client. Spec Kit's /speckit-constitution needs principles to write down, and nobody has them in one place.

Agents
kb-vaultdomain-analyzermethodologytest-strategydeployment-strategyconstitution
The flow
  1. /speckit-spectra-kb-vault with the external documents attached. It shows you a table of where each one will land and waits for approval. Policy documents (a test handbook, a hosting standard) go into their own <kind>-source/ folders for the owning agent to read later.
  2. /speckit-spectra-domain-analyzer → /speckit-constitution It infers the business domain from the code and docs, and you decide each candidate guardrail. Paste its ready-made prompt to create the constitution. Add Artifact root: docs/ on this first run.
  3. /speckit-spectra-methodology → /speckit-constitution It reads the git history, PR templates, and CI to find how the team actually works, asks ten questions, and you amend the constitution with the result.
  4. /speckit-spectra-test-strategy → /speckit-constitution Test levels and a coverage floor no higher than today's baseline. Amend again.
  5. /speckit-spectra-deployment-strategy → /speckit-constitution Environments, gates, rollback. Amend a final time.
Run the constitution after each agent, not once at the end. Each later agent then finds a ratified constitution, proposes only what it does not already say, and never offers you a rule twice. The imported documents are treated as what someone claimed; the code and history decide what is actually true.
You end up with a constitution built from evidence and your decisions, plus DOMAIN_ANALYSIS.md, ENGINEERING_METHODOLOGY.md, TEST_STRATEGY.md, and DEPLOYMENT_STRATEGY.md that explain where every rule came from.

Greenfield? Skip the import and start at the domain analyzer. The order is otherwise the same.

02

Unstructured documentation

The situation: the knowledge your team relies on is scattered. ADRs from a previous vendor sit in a PDF, the UX standards are a slide deck, the onboarding guide is a Word file, and a key diagram exists only as a screenshot. Neither new people nor coding agents can find any of it.

Agents
kb-vault
The flow
  1. Attach everything to /speckit-spectra-kb-vault (or dictate what you know when there is nothing to attach). It works out what kind of document each source is and how this repository already keeps its docs.
  2. Review the plan table. Category, description, destination, create or update. Nothing is written until you approve. Changing anything re-presents the whole table.
  3. Approve, then review the uncommitted Markdown. ADRs join your existing docs/adr/ set with its numbering and template. Documents that match something already in the repo update it in place instead of creating a duplicate. Everything else gets its own category folder with an index.
You end up with the team's knowledge as Markdown in the repository, traceable to the sources you supplied. kb-vault never invents content, never mines your code, and never commits.
03

From a business ask to a spec

The situation: a stakeholder sends a two-line email: "support agents need to merge duplicate tickets." You could paste it straight into /speckit-specify, but you would get a spec built on assumptions, and nobody knows yet what in the system it would touch.

Agents
brdimpactspecifyclarifychecklist
The flow
  1. /speckit-spectra-brd with the email text or attached document. It asks a few questions only where the requirement has gaps, and writes a structured BRD without inventing requirements.
  2. /speckit-spectra-impact with a paragraph of intent. Before anyone commits, it reports what the change would touch, with a path:line citation and confidence level for every finding.
  3. /speckit-specify fed the BRD, then /speckit-clarify to close what is still vague.
  4. /speckit-checklist to score the spec for completeness and consistency before planning.
You end up with a spec grounded in a reviewed BRD and an evidence-backed impact analysis, so the scope conversation happens before planning, not during code review.
04

TDD on top of SDD

The situation: the team wants test-first development. Spec-driven development stays the base, but tests should be agreed from the spec and written before the code they cover. "We do TDD" in a README is not enough; it needs to be an obligation each phase actually checks.

Agents
methodologyconstitutiontest-strategyspecifytest-planplantasksimplementconverge
Once per project
  1. /speckit-spectra-methodology Choose the TDD overlay (for example, "MUST for features and fixes, new and changed code"). It becomes a set of obligations tied to Spec Kit phases, then goes into the constitution through its ready-made prompt.
  2. /speckit-spectra-test-strategy so later test plans know which test levels exist and what coverage floor applies.
For every feature
  1. /speckit-specify writes the spec. A hook then offers the test plan.
  2. /speckit-spectra-test-plan turns the spec into a test plan stakeholders approve: every acceptance criterion traced to a test condition or flagged as uncovered.
  3. /speckit-plan with the test plan's ready-made prompt, which adds a Testing obligations section to plan.md.
  4. /speckit-tasks Each test task now precedes and blocks the implementation task it covers.
  5. /speckit-implement A test task records a failing run before its implementation task can be ticked. A bug fix starts with a failing regression test.
  6. /speckit-converge checks the build against spec, plan, and tasks, and appends anything missing as new tasks.
You end up with test-first as a binding rule every phase enforces, with evidence in tasks.md that each test failed before its code existed.
05

User acceptance testing

The situation: the feature is implemented and the unit tests pass. Before a PR goes up, someone needs to confirm it works the way the user story described, on the real build, and keep proof.

Agents
test-plantasksimplementuatcreate-pr
The flow
  1. Earlier, /speckit-spectra-test-plan suggested UAT scenarios for every user story. /speckit-tasks turned them into a final UAT phase that /speckit-implement leaves open.
  2. After implement, accept the hook's offer: /speckit-spectra-uat specs/001-signup It shows the exact command it would use to start the build and waits for your confirmation.
  3. It performs the scenarios it can drive and saves screenshots and transcripts under specs/<feature>/uat/<run>/. It ticks only what it saw pass. Human-only or failing scenarios stay open, with a reason.
  4. A person finishes the rest, then /speckit-spectra-create-pr opens the PR.
You end up with a uat-report.md and linked evidence for every ticked scenario. The UAT agent never edits code to make a scenario pass.
06

Specification status

The situation: a feature has been "nearly done" for a week. Every box in tasks.md is ticked, but you are not sure the code matches what the spec promised, or whether the spec drifted while the plan changed.

Agents
analyzeconvergeuatreview-pr
Ask, depending on where the feature is
  1. Before the build: /speckit-analyze Do the spec, plan, and tasks still agree? Finds drift, gaps, and contradictions.
  2. After the build: /speckit-converge Does the code deliver what the spec, plan, and tasks say? Gaps become new tasks for implement.
  3. Does it work for a user? /speckit-spectra-uat The UAT report shows which scenarios passed with evidence and which are still open.
  4. At the PR: /speckit-spectra-review-pr Catches what a diff-only review cannot: a task marked complete but missing from the change, or scope no requirement authorized.
You end up with a status you can defend: "converged, UAT 7 of 8 with evidence, one scenario waiting on a human" instead of "should be done."
07

A big decision mid-feature

The situation: while planning, the team decides to move session storage from the database to Redis. It will shape the next ten features, and in six months nobody will remember why.

Agents
adrconstitutionplanreview-pr
The flow
  1. /speckit-spectra-adr We should move session storage to Redis It reads the code, earlier ADRs, and the constitution, asks a few questions, and writes the record under docs/adr/. If the decision is significant enough to govern later work, it also drafts guardrails for you to approve and ends with a ready-made constitution prompt. It never edits the constitution itself.
  2. /speckit-constitution with that prompt, to amend the constitution. The new rule cites the ADR it came from. If the agent judged the decision not significant, it says why and you skip this step.
  3. /speckit-plan now plans against a binding rule instead of a conversation, and its Constitution Check tests the plan against it.
  4. Later, /speckit-spectra-review-pr flags any PR that uses a pattern an ADR rules out.
You end up with the decision, its alternatives, and its consequences in the repository, made binding in the constitution, and enforced at review time.
08

A production defect

The situation: a ticket comes in: orders are occasionally charged twice. The first plausible code path is tempting, but it was patched last quarter too, and the bug came back.

Agents
defect-rcaspecifyimplement
The flow
  1. /speckit-spectra-defect-rca https://github.com/acme/orders/issues/412 It reads the code, commits, config, and tests before asking you anything, and checks whether this defect was analyzed before and whether the earlier preventive actions were actually done.
  2. Read the analysis. Every claim cites a file and line. Rejected hypotheses are listed beside the surviving one, and it says plainly when it has only reached the immediate cause rather than the systemic one.
  3. Fix it through Spec Kit. Specify the fix from the RCA. With the TDD overlay, implement starts with a failing regression test.
You end up with a root cause backed by evidence and a fix aimed at it, not the symptom. The RCA agent fixes nothing and never touches your ticket.
09

A flaky test suite

The situation: CI goes red one run in five on the same commit. People have started re-running the pipeline until it passes, which means a real failure would be ignored too.

Agents
flaky-test-detector
The flow
  1. /speckit-spectra-flaky-test-detector It reads your test source (no CI integration, no run history needed) and reports each likely flaky test with a confidence rating and a specific fix.
  2. Approve a task list, prune it, then approve again and it fixes what is left one item at a time, ticking each off on disk so an interrupted session resumes where it stopped.
You end up with causes removed, not hidden. Deleting assertions, skipping tests, and adding retries are not allowed as fixes, and it never runs your suite.
10

Shipping and reviewing

The situation: the feature is built and accepted. It needs a correctly targeted PR, and the reviewer needs to check it against what was agreed, not just read the diff.

Agents
create-prreview-pr
The flow
  1. /speckit-spectra-create-pr --issue 42 (also offered after implement). It offers to commit and push, confirms once, and returns the PR URL.
  2. The reviewer runs /speckit-spectra-review-pr It reads the spec, ADRs, and constitution at the PR's own revision. Findings land on the line they are about, and only blockers and majors are proposed by default.
  3. You choose what to publish. One review goes up under your own credentials, containing only the findings you selected.
You end up with a review measured against the spec, plan, and guardrails the PR carries, without a flood of nitpicks.
