Agent reference

What each SPECTRA agent does, what it takes, and how to run it.

Spectra ships as a single extension under the unified speckit.spectra.* namespace — install once and get every command. Examples use Claude's trigger form — a leading slash with dashes, like /speckit-spectra-adr. Other agents differ (kiro-cli uses /speckit.spectra.adr); your agent's own command list shows the exact trigger.

    How it works

    It is built for an existing codebase that has never had a constitution, and it works with one that has.

    1. Says first whether it found .specify/memory/constitution.md, and so whether this run's goal is to create the constitution or update it.
    2. Reads your project — constitution, docs and specs, source code and dependency manifests, and any prior analysis — and infers your business domain from the evidence.
    3. Works six lenses: domain and business rules, data sensitivity and regulation, security and trust boundaries, architecture and boundaries, technology and dependency policy, and reliability and operability. Each candidate guardrail cites a file and says whether the code already follows it (observed) or not (aspirational). Testing, deployment, and workflow policy are left to test-strategy, deployment-strategy, and methodology.
    4. Asks you seven questions, one at a time: the domain, then one per lens. Each has at least four options, one recommended and one Skip, and free text always works.
    5. Only after the last answer, writes docs/DOMAIN_ANALYSIS.md — or DOMAIN_ANALYSIS.md at your declared artifact root — recording every candidate and decision, plus the Constitution input section holding exactly what you accepted. It is shaped by domain-analysis-template (override at .specify/templates/overrides/domain-analysis-template.md).
    6. Ends with a link to the file and a ready-to-paste /speckit-constitution prompt that creates or amends the constitution from that section.

    Skip, an unanswered question, and --non-interactive all adopt nothing.

    Re-running and upgrading

    Re-running offers your previous answers as each question's proposed answer, so it confirms rather than asks again. A guardrail you reworded keeps its ID, and one you declined is not offered back to you as new. An accepted guardrail the constitution now carries is marked status: adopted and leaves the Constitution input section, so a second /speckit-constitution run does not adopt it twice.

    From an earlier version:

    • An analysis left at .specify/memory/domain-analysis.md is read on the next run, so your decisions carry over; the command reports it and leaves it for you to remove.
    • A checkbox file is read as your prior decisions: ticked means accepted, and unticked items are asked about again, since an unticked box cannot say whether anyone looked at it.
    • Delivery and workflow decisions are kept as a record, handed on to methodology, and leave the Constitution input section.

    How it works

    1. Says first whether the project is brownfield or greenfield — from three signals: source beyond scaffolding, workflow configuration, and more than 10 commits — and whether this run's goal is to create the constitution or update it. With exactly one signal it asks you to settle the reading.
    2. Reads git log and git branch -a, PR and issue templates, CODEOWNERS, CI workflows, commit and changelog configuration, CONTRIBUTING.md, specs/, the constitution, and the sibling documents — accepted entries only.
    3. Works nine lenses: methodology stack, work modes and classification, requirements intake, spec lifecycle and traceability, branching and integration, review and merge gates, change records, AI collaboration rules, and governance and evolution. In brownfield mode each reports current practice with citations before proposing; in greenfield mode each offers defaults.
    4. Treats spec-driven development as the base, and offers TDD, BDD/ATDD, DDD, contract-first, and ADR-driven as overlays, each with its evidence. An adopted overlay becomes obligations bound to specify, plan, tasks, or implement — TDD's implement obligation is checked in tasks.md — with a strictness (MUST or SHOULD) and a scope you choose.
    5. Asks you ten questions, one at a time. Each has at least four options, one recommended and one Skip, and free text always works.
    6. Only after the last answer, writes docs/ENGINEERING_METHODOLOGY.md — or ENGINEERING_METHODOLOGY.md at your declared artifact root — with a mode-choice table, branch-naming and commit-prefix references, the obligations matrix, and a Constitution input section holding exactly what you accepted. It is shaped by engineering-methodology-template (override at .specify/templates/overrides/engineering-methodology-template.md).
    7. Ends with a ready-to-paste /speckit-constitution prompt, then lists the other constitution-feeding agents you have not run yet.

    It never edits the constitution, never runs another spec-kit phase, and never proposes in a sibling's ground: test levels and coverage stay with test-strategy, environments and versioning with deployment-strategy, product technology and domain content with domain-analyzer. A hand-written methodology already at the path is read as evidence and replaced only with your consent.

    Re-running and upgrading

    KB Vault

    Foundation
    speckit.spectra.kb-vault Get the knowledge your team already has into the repository, where people and coding agents can both read it. Attach the documents — a PDF of architecture decisions inherited from a previous team, a Word file describing the engineering workflow, a deck of UX/UI standards, a diagram exported as an image — or just describe what you know. It absorbs all of it, works out what kind of document each source is, learns how your project already keeps documentation, and writes Markdown.
    Arguments: optional. Steering for the attached documents, or the knowledge itself when you have nothing to attach. With neither an argument nor a document it asks for material and stops.
    Examples (Claude) 
    /speckit-spectra-kb-vault
    /speckit-spectra-kb-vault these are our UX standards and the old architecture decisions
    Full reference

    Get the knowledge your team already has into the repository, where people and coding agents can both read it. Attach the documents — a PDF of architecture decisions inherited from a previous team, a Word file describing the engineering workflow, a deck of UX/UI standards, a diagram exported as an image — or just describe what you know. It absorbs all of it, works out what kind of document each source is, learns how your project already keeps documentation, and writes Markdown.

    It shows you a table before it writes anything. Category, description, destination, create or update — one row per document it intends to produce, with the unreadable sources, the merges, the contradictions and the redactions named beneath it. Then it stops. This is the one Spectra document agent that gates on approval rather than showing you the result, because it is aimed at repositories that already have documentation, where an unwanted update is not trivially undone by someone who did not notice it happened. A comment on the plan is not approval of it; any change re-presents the whole table; an ambiguous answer writes nothing.

    It updates what you already have rather than duplicating it. Supply a revised standards document and it finds the one in your repository — matching on subject and category, never on title similarity, because standards.md and ux-guidelines.md may well be the same document while adr-005.md and adr-006.md certainly are not. It edits that file in place, at its existing path, keeping its name and the hand-written sections your source never mentions. The match is labelled as a judgement, so a wrong one costs you a sentence to correct and does not cost you another pass over your attachments.

    It never invents, and it never mines your codebase. Every substantive sentence traces to something you supplied. A template section with no source says so instead of being filled. A file it cannot read is named and its content requested — never guessed at from the filename, because invented documentation is indistinguishable from the real thing once committed. A diagram is transcribed only as far as it is legible, and where the structure will not carry it says that rather than implying a picture is present. And "document the architecture" with nothing attached gets you a request for material, not documentation reverse-engineered from your source code.

    It joins your existing sets instead of starting new ones. Where a supplied document is a kind Spectra already produces — an ADR, a BRD, an impact analysis, a defect RCA — it adopts that agent's folder, numbering and template. Without that rule, a PDF of past architecture decisions would land in a folder of its own beside the one the ADR agent maintains: two decision records, two numbering schemes, and no rule for which is authoritative. A domain analysis, engineering methodology, test strategy, or deployment strategy is different: those documents feed the constitution and belong to the agent that produces them, so kb-vault never writes them. It keeps the source as a policy source in its own <kind>-source/ folder, and the plan and report name the agent to run next, which reads it as what the document claims.

    • Arguments — optional. Steering for the attached documents, or the knowledge itself when you have nothing to attach. With neither an argument nor a document it asks for material and stops.
    • Use it when — onboarding a repository that has knowledge living in PDFs, decks and people's heads; folding an acquired or inherited project's documentation into the tree; or writing down a process you have never written down.
    • Your guardrails bind it — it reads your constitution before planning, honours your declared artifact root, and where a supplied document conflicts with a stated principle it surfaces the conflict and asks rather than writing the contradiction. It never amends the constitution to fit.
    • Where it writes — <artifact-root>/<category>/ per document, plus a rebuilt index in each category folder it owns. New files never leave that root; an update goes where the document already lives, which is the one deliberate departure and the reason "update, don't duplicate" works on a project whose documentation predates Spectra. Your supplied originals stay outside the repository.
    • It never commits — when the files are written it tells you they are uncommitted and hands the review back to you.

    The plan is the safety mechanism

    This is the only Spectra document command that gates on approval rather than showing you the result, and the reason is that it is aimed at repositories that already have documentation. An unwanted new file is noticeable; an unwanted update to a document someone else wrote is not. So a comment on the plan is not approval of it, any change re-presents the whole table, and an ambiguous answer writes nothing. Declining costs you nothing — git status is unchanged.

    You can move a row to a different category folder, rename it, drop it, split it, merge it, or convert a create into an update. The one thing you cannot do is send a new file outside your artifact root; ask for that and it offers the two routes that get you there properly — the Artifact root: declaration line, or a git mv you run afterwards.

    It joins your existing sets instead of starting new ones

    Where a supplied document is a kind Spectra already produces, it adopts that agent's folder, numbering and template:

    What it will not do

    It never invents. Every substantive sentence traces to something you supplied; a template section with no source says so instead of being filled; a file it cannot read is named and its content requested rather than guessed at from the filename. It never mines your codebase for content — it reads your project to decide where a document goes and what shape it takes, never what it says, so "document the architecture" with nothing attached gets you a request for material. Your supplied originals stay outside the repository; you get Markdown. And it never stages, commits, branches, pushes, tags or opens a pull request — when the files are written it tells you they are uncommitted and hands the review back.

    Change the shape of your knowledge documents

    The default structure is a shipped template. To change it for your whole team, permanently, copy it to .specify/templates/overrides/kb-document-template.md and commit it — or shape a single category with .specify/templates/overrides/<category>-template.md, which applies even to a category Spectra has never heard of. Do not edit the installed copy under .specify/extensions/: the next extension update replaces it. Every run reports which template it resolved, by full path, so an override that failed to apply is visible rather than silent.

    How it works

    1. Absorbs every supplied source in full, reporting per file whether it could read it.
    2. Resolves your artifact root, then reads how your project already keeps documentation — folders, numbering, document shapes, templates, indexes.
    3. Classifies each source into a category, from its content rather than its filename.
    4. Looks for a document you already have about the same subject, and plans an update to it rather than a second file beside it.
    5. Shows you a table — category, description, destination, create or update — and stops.
    6. Writes only after you approve, and only what the approved table says.

    Decide how this project tests itself, once, at the start. It reads the repository, works out for itself whether this is greenfield or brownfield, and writes one strategy to docs/TEST_STRATEGY.md — or your declared artifact root — covering unit, integration, API contract, end-to-end, UAT, and regression testing plus a coverage floor. Then it drafts the guardrails that would hold every future work session to it, records your decision on each, and hands a Constitution input section to /speckit-constitution — to create the constitution when there is none, or to update it.

    Before it writes, it asks you five things — one at a time, each arriving with the answer it would have chosen and the evidence behind it. Where the testing weight should sit, whether anything outside the repository depends on an interface here, which journeys justify an end-to-end test, what has broken that your tests did not catch, and what constraints the repository does not show: no container runtime in CI, a freeze on new dependencies, a compliance rule. That last one is the gap worth closing — it already refused to name a tool your stack cannot run, but had nothing to say about one your stack can run and your team may not adopt. It will not ask you anything it can measure. Not the mode, not the stack, not the surfaces, not your coverage figure; those it reads, because a wrong answer would outrank a right one. And declining is free: say "use your defaults" and you get the document it would have written on its own, for the cost of one reply. --non-interactive skips the round entirely.

    It is deliberately hard for it to say something plausible and wrong. Every recommendation either cites a path in your project, is marked as a convention with no project evidence, or is marked stated and names the question you answered — never neither, and never an answer dressed up as evidence. An answer never moves a number: ask for a 90% floor in a repository measuring 31% and the floor stays at 31%, with the disagreement recorded in the document rather than argued at you. It will not name a tool your stack cannot run, so the end-to-end lens resolves to browser, HTTP, CLI, or none rather than reaching for a browser driver; for a published library, none is the correct answer and it says so. When it claims something is missing, it tells you what it searched for and where.

    Brownfield is where most of the care went. It reads your source rather than your README, reports what each lens covers today before proposing anything, and never proposes a floor above your current baseline — a floor that fails the next build gets deleted, and a deleted floor is worth less than none. Coverage figures carry their provenance: measured only if it ran your tool this session after asking permission, reported with the report's date if it read a committed file, unavailable if there is nothing to read. Where the floor sits below the target, the ratchet is written as triggers you can check from the repository, not as dates it has no way to know.

    The last two lenses are policy rather than levels. UAT states whether acceptance testing applies, who may perform it — a human, or an AI agent only on explicit request — and what counts as evidence on each surface this project actually has: a screenshot for a browser, a transcript for a CLI or an HTTP call. Regression names the suite that must stay green, cites where it runs or says it runs nowhere automatically, and records whether a fixed defect earns a regression test. Both are marked applicable or not, with the reason, and both are recorded in the document's front matter — the lens set and which level owns what — so test-plan can read them rather than guess. The drafted guardrails gain one that keeps UAT out of the implement command's hands.

    Two things it will not do. It never writes your constitution — not on approval, not on a re-run, not if you insist. It drafts each guardrail under a frozen ts- ID, records whether you accepted, declined, or skipped it, and tells you the command that applies the accepted ones, because one command should own constitution edits and the sync impact report that goes with them. A document imported by kb-vault is read as what it claims, never as current practice. And it never applies configuration: the exact CI or coverage change is written out for you to make.

    Unlike the other document agents, it produces a singleton — one file at a fixed path, rewritten in place on a re-run, with Git carrying the history. A standing policy has exactly one current answer, and anything that links to it should not break every time you refresh it.

    • Arguments — none required. Optionally pass a focus to weight the analysis; it never narrows the six mandatory lenses.
    • Use it when — setting up a new project before the first feature, or landing Spectra on an established codebase and wanting a testing baseline that starts from what is already there.

      /speckit-spectra-test-strategy /speckit-spectra-test-strategy focus on the API contract boundary with the payments service

    How it works

    1. Reads your project — constitution, specs, docs, dependency manifests, test and coverage configuration, CI definitions, and, in a brownfield repository, the source itself.
    2. Classifies the project greenfield, brownfield, or mixed from evidence, never by asking you, and reports the signals that decided it — including any that pointed the other way.
    3. Identifies the testable surfaces, so a monorepo does not get one answer for three stacks.
    4. Asks you its five questions, one at a time.
    5. Works six lenses — unit, integration, API contract, end-to-end, UAT, regression — each either applicable with a named approach or not applicable with a stated reason.
    6. Derives a coverage floor from the baseline it could establish, with a ratchet toward the target.
    7. Writes one document to docs/TEST_STRATEGY.md, or TEST_STRATEGY.md at your declared artifact root.
    8. Checks whether the strategy is already in your constitution — or whether there is one at all — drafts the guardrails it would make binding, records your decision on each, and hands a Constitution input section to /speckit-constitution.

    It runs nothing without your explicit confirmation — not even your coverage tool.

    Re-running and upgrading

    On a re-run it marks what the constitution has since adopted, never offers a declined guardrail again as new, and reads a strategy from before 1.25.0 without losing a ticked decision.

    Change the shape of the strategy

    The document's twelve sections are overridable at .specify/templates/overrides/test-strategy-template.md.

    How it works

    1. Reads the requirement — inline text, or a .docx/.pdf/.md/.txt document whose text it extracts. Unreadable or image-only files are reported, not fabricated.
    2. Reads project context — the shipped BRD template, the constitution, existing BRDs under docs/brd/, and prior specs — to ground and deconflict, without adding scope the requirement didn't state.
    3. Writes one BRD to docs/brd/NNN-<title>.md (folder created automatically, numbered zero-padded to three digits, never overwriting), following the canonical template — genuine unknowns become Open Questions and adopted defaults become Assumptions.
    4. Reports the path and tells you to run the Spec Kit specify command with the BRD.

    Its only write is the BRD file; it never edits your spec, constitution, or source, and never invokes specify itself.

    Publishing and upgrading

    Artifact root: documents/ in .specify/memory/constitution.md sends BRDs to documents/brd/ instead of docs/brd/. The command checks whether docs/ is a published site source before defaulting there and asks first if it is; a BRD carries stakeholders, revenue targets, and competitive rationale, so publishing one by accident is the mistake worth one question. Unanswered, it picks the non-publishing folder.

    Upgrading from an older version? A brds/ folder from before 1.6.0 is read for context and numbering, so the next BRD continues the sequence; the command says once where BRDs live now and offers a git mv. Nothing in the old folder is moved or modified.

    Change the shape of your BRDs

    Same mechanism as the ADR agent, with brd-template.md:

    mkdir -p .specify/templates/overrides
cp .specify/extensions/spectra/templates/brd-template.md .specify/templates/overrides/brd-template.md

    Commit it, and every BRD follows your structure — the 14 shipped sections are a default, not a fixed contract. Resolution order, the reported template path, and the survives-updates guarantee are identical to the ADR agent's, described above.

    One caveat worth knowing: Section 6 — User Journeys is what the Spec Kit specify command leans on most heavily. Dropping it is allowed, and the command will say it did so, but expect the resulting spec to have thinner user stories.

    Impact Analyzer

It never edits source, CI, manifests, or infrastructure code, runs nothing, and makes no network request. Like the test strategy, it is a singleton, rewritten in place on a re-run, with your previous answers offered back for confirmation.

    • Arguments — none required. Optionally a focus, paths to local documents, and --non-interactive.
    • Use it when — a project is about to ship its first release, or an established project's deployment practice has grown by accretion and needs writing down as one policy.
    • Examples (Claude)
      /speckit-spectra-deployment-strategy /speckit-spectra-deployment-strategy ./client/hosting-standard.md focus on the pre-release gate

    What it reads and records

    Besides the CI, container, orchestration, infrastructure and migration files, it reads your constitution, specs, ADRs, docs, and release configuration, and any TEST_STRATEGY.md or DOMAIN_ANALYSIS.md already written.

    A convention claim is a default with nothing behind it. Each guardrail it drafts is recorded under a frozen ds- ID along with your decision on it.

    The document's twelve sections are overridable at .specify/templates/overrides/deployment-strategy-template.md.
