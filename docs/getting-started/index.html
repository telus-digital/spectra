Spec-driven development & Spec Kit

Write down what you are building before an agent builds it.

SPECTRA sits on top of GitHub Spec Kit, and Spec Kit is an implementation of an idea: spec-driven development. This page covers the idea and the toolkit. The next page covers what SPECTRA adds.

01The problem it solves

Coding agents are fast and capable, but a one-line prompt leaves most of the decisions unstated. The agent fills those gaps with guesses: which edge cases count, which libraries to use, what "done" means. The result often looks right and is subtly wrong, and nobody wrote down what it was supposed to do, so nobody can check it.

Spec-driven development (SDD) turns that around. The specification is the primary artifact and the code is generated from it. You state the intent first (what the user needs and why), then the plan (how, within your constraints), then the tasks. Each step is a document a person can read, question, and approve before the next one starts.

Vibe coding asks "can the agent build something?" Spec-driven development asks "did the agent build the thing we agreed on?" You can only answer the second question if the agreement was written down.

02Part of AI-native engineering

In AI-native engineering, agents write most of the code. Engineers direct them: they write the specifications, manage what the agents know, and check what comes back. It rests on four practices, and spec-driven development is the one the other three are organized around.

The core

Spec-driven development

Requirements and a plan are written down and agreed before any agent generates code.

Context engineering

Agents get lasting rules, project conventions, and the right documents, so they work from the facts of this project instead of guessing.

Human orchestration

The engineer's job moves from typing code to deciding what happens next, setting limits, and reviewing what each step produced.

Rigorous verification

Tests, reviews, and quality gates decide whether the output is accepted. Nothing is taken on trust because an agent produced it.

03The spec-driven loop

Every feature goes around the same loop. Each phase writes a document, and the spec at the centre is what every later phase reads and is checked against.

A human checkpoint: you review what the phase wrote before the next one starts.

What changes

Intent before implementation

The spec says what and why, with no tech stack in it. Technical choices come later, in the plan, where they can be weighed against the spec.

Guardrails written once

A constitution holds the project's non-negotiables: architecture, security, testing, quality. Every later phase is checked against it.

Checkpoints a human holds

Each phase ends in a file you review. Ambiguity is cleared up in the spec, where it is cheap, instead of in a pull request, where it is expensive.

04Spec Kit: SDD in practice

GitHub's Spec Kit is an open-source toolkit for SDD. It installs as the specify CLI, sets up a project's .specify/ folder, and gives your coding agent a slash command for each phase. It works with Claude Code, GitHub Copilot, Cursor, Codex, and many others. It puts the spec-driven loop into practice, together with the other three practices:

Human orchestration

You run every phase. Each phase is a slash command you type. The agent does that phase's work and stops, and nothing moves on until you start the next command.

Context engineering

Everything lives in the repository. The constitution sits in .specify/memory/, and each feature's spec, plan, and tasks sit together in specs/<feature>/, versioned with the code. Every phase reads what came before it, not the chat history.

Rigorous verification

A human in the loop after every phase. Each phase ends in a file you review and approve. Along the way, clarify questions the gaps, the plan is checked against the constitution, analyze cross-checks the documents, and converge checks the build against all of them.

Phase by phase
FOUNDATION /speckit.constitution

Set the principles every feature must respect.

constitution.md
01 · WHAT /speckit.specify

Describe the feature: user stories, acceptance criteria, no tech stack.

spec.md
02 · CLARIFY /speckit.clarify

Targeted questions about the gaps, answered back into the spec.

spec.md (updated)
03 · HOW /speckit.plan

Tech stack, architecture, data model, contracts, checked against the constitution.

plan.md
04 · STEPS /speckit.tasks

An ordered, dependency-aware task list.

tasks.md
05 · CHECK /speckit.analyze

Cross-check spec, plan, and tasks for drift before anything is built.

report
06 · BUILD /speckit.implement

Execute the tasks in order, building to the spec.

code + tests
07 · CONVERGE /speckit.converge

Check the finished build against spec, plan, and tasks, and append any gaps as new tasks.

tasks.md (updated)

Also available: /speckit.checklist scores the spec's quality ("unit tests for requirements"). The exact trigger form depends on your agent; Claude Code, for example, uses /speckit-specify.
